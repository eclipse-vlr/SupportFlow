# Устройство и разработка SupportFlow

Подробности API, очереди и проверок.

## Устройство проекта

```text
cmd/supportflow/       запуск, конфигурация зависимостей, остановка
cmd/eval/              проверка классификации на учебных обращениях
internal/ticket/       типы обращения, анализа и проверки оператором
internal/httpapi/      HTTP API и встроенная страница оператора
internal/store/        PostgreSQL, схема, очередь и операции с обращениями
internal/llm/          адаптер Responses API и отдельный демопровайдер
internal/worker/       фиксированное число фоновых обработчиков
internal/config/       чтение и проверка переменных окружения
testdata/eval.json     32 размеченных учебных обращения
```

Типы и проверки в `ticket` не зависят от SQL, HTTP и конкретной модели. HTTP и фоновые обработчики определяют небольшие интерфейсы для необходимых им операций. PostgreSQL и LLM-клиент реализуют внешние эффекты.

Путь одного обращения:

1. API проверяет JSON, длины полей и ключ повторного запроса.
2. В одной транзакции проверяет вместимость очереди и сохраняет обращение со статусом `pending`.
3. Обработчик атомарно забирает задачу через `FOR UPDATE SKIP LOCKED`: статус `processing`, номер попытки, срок аренды.
4. Вызывает модель с таймаутом, проверяет структуру и значения ответа.
5. Сохраняет анализ и токены: `completed`. Временная ошибка возвращает задачу в очередь с задержкой; постоянная ошибка или исчерпание попыток приводит к `failed`.
6. Оператор сохраняет отдельную проверку. Исходный анализ модели сохраняется.

Очередь находится в PostgreSQL; отдельный брокер для этого MVP не нужен. Незавершённая задача после истечения аренды доступна для повторного захвата. Номер попытки служит версией: запоздалый старый обработчик не может записать результат поверх новой попытки. Просроченная последняя попытка переводится в `failed`.

При остановке приложение прекращает приём HTTP-запросов, завершает принятые HTTP-запросы, отменяет обработчики и дожидается их выхода. Незавершённые задачи остаются в базе для восстановления.

## HTTP API

Все пути API имеют префикс `/api/v1`. Тела запросов — JSON; максимальный размер тела 32 КиБ, текст обращения — 16 КиБ, тема — 200 символов. Неизвестные и повторяющиеся поля, дополнительные JSON-документы и неверная кодировка отклоняются до записи в БД.

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/v1/tickets` | Создать обращение, `202`; повтор — `200` |
| GET | `/api/v1/tickets/{id}` | Получить обращение со статусом и анализом |
| GET | `/api/v1/tickets` | Список: `category`, `status`, `limit`, `offset` |
| PATCH | `/api/v1/tickets/{id}/review` | Сохранить категорию, черновик и подтверждение |
| GET | `/api/v1/config` | Текущий провайдер, без секретов |
| GET | `/healthz` | Процесс отвечает |
| GET | `/readyz` | PostgreSQL доступна |

Создание через PowerShell:

```powershell
$payload = @{
    title = 'Нет доступа после оплаты'
    message = 'Оплатил подписку, но доступ не появился.'
} | ConvertTo-Json

$ticket = Invoke-RestMethod `
    -Method Post `
    -Uri 'http://localhost:8080/api/v1/tickets' `
    -ContentType 'application/json; charset=utf-8' `
    -Headers @{ 'Idempotency-Key' = [guid]::NewGuid().ToString() } `
    -Body ([System.Text.Encoding]::UTF8.GetBytes($payload))

Invoke-RestMethod "http://localhost:8080/api/v1/tickets/$($ticket.id)"
```

Для повторной отправки после сетевого сбоя используйте **тот же** `Idempotency-Key` и те же данные: вернётся исходное обращение. Тот же ключ с другим содержимым даёт `409`. Без ключа каждый запрос считается новым.

Категории: `billing`, `access`, `technical`, `other`. Приоритеты: `low`, `medium`, `high`. Фильтр по категории учитывает последнюю правку оператора. Список упорядочен по времени создания, `limit` от 1 до 100, `offset` от 0 до 10000. Это живой список: новые обращения могут сдвигать страницы.

Проверка оператором доступна только после завершения анализа:

```json
{
  "category": "billing",
  "draft_reply": "Здравствуйте! Уточните, пожалуйста, дату оплаты.",
  "approved": true
}
```

`approved: false` сохраняет черновик. Хранится последняя версия правки; при одновременном редактировании действует последняя сохранённая правка.

## Ограничения нагрузки и расхода

| Переменная | По умолчанию | Значение |
|---|---|---|
| `LLM_PROVIDER` | `demo` | `demo` или `openai` |
| `WORKERS` | `2` | Число параллельных обработчиков, максимум 16 |
| `LLM_TIMEOUT` | `30s` | Таймаут одной попытки, от 1s до 2m |
| `MAX_ATTEMPTS` | `3` | Попытки обработки одной записи, максимум 5 |
| `MAX_OUTPUT_TOKENS` | `1500` | Лимит выходных токенов одной попытки, максимум 8000 |
| `MAX_QUEUED_TICKETS` | `100` | Вместимость активной очереди, максимум 10000 |
| `HTTP_PORT` | `8080` | Локальный порт приложения в Compose |
| `DATABASE_PORT` | `55433` | Локальный порт PostgreSQL в Compose |
| `POSTGRES_PASSWORD` | `supportflow_local` | Пароль локальной учебной БД |

`408`, `429`, `5xx` и сетевые ошибки повторяются в пределах лимита попыток. Учитывается `Retry-After`, применяется экспоненциальная задержка со случайной добавкой. Ошибки доступа, отказ модели, неподходящий JSON и обрезанный ответ завершают задачу без автоматического повторного расхода.

При заполнении активной очереди новые обращения получают `429`. Проверка вместимости сериализована транзакционной advisory-блокировкой, поэтому параллельные запросы не превышают лимит.

В записи суммируются **известные** токены из полученных ответов. При сетевом обрыве или сбое между ответом провайдера и записью в БД фактический расход может быть больше. Обработка имеет семантику at-least-once: аренда защищает запись результата, но не исключает повторный оплачиваемый вызов. Жёсткий месячный бюджет нужно устанавливать у провайдера. Приложение не рассчитывает стоимость по изменяющимся тарифам.

## Проверки

Полная проверка в Docker, включая настоящую PostgreSQL и race detector:

```powershell
docker compose --profile tools run --rm check
```

Команда проверяет форматирование, выполняет `go vet`, `go test -race`, `go mod verify`, затем проверяет демоправила на 32 примерах. **Последний шаг проверяет только демоправила, а не качество модели.**

Форматирование:

```powershell
docker compose --profile tools run --rm --no-deps check gofmt -w cmd internal
```

При доступном локальном Go 1.26+:

```powershell
go test ./...
go vet ./...
```

Без `TEST_DATABASE_URL` интеграционные тесты PostgreSQL пропускаются. Для их локального выполнения задайте строку подключения к тестовой БД. Каждый тест создаёт собственную схему и удаляет только её; нужны права на `CREATE SCHEMA`. Для `go test -race` вне Docker нужен рабочий C toolchain.

Тесты покрывают: ограничения и ошибки API до записи, контракт Responses API, отказы и неполные ответы, отмену активного HTTP-запроса к провайдеру, повторы и остановку обработчика, конкурентный приём задач, единственного владельца аренды, восстановление просроченной задачи и запрет записи устаревшим обработчиком, сохранение правки оператора и токенов.

Оценка настоящей модели — отдельный осознанный запуск с расходом токенов. В окружении должны быть `LLM_PROVIDER=openai` и `OPENAI_API_KEY`:

```powershell
go run ./cmd/eval -limit 5
```

`-limit 0` обрабатывает все 32 примера. Команда делает одну попытку на пример, выводит точность категории и ошибки. Корректность черновиков требует ручной оценки. Этот небольшой синтетический набор предназначен для обучения, а не для вывода о качестве на реальных клиентах.

## Локальный запуск без контейнера приложения

```powershell
docker compose up -d db
$env:LLM_PROVIDER = 'demo'
$env:HTTP_ADDR = '127.0.0.1:8081'
$env:DATABASE_URL = 'postgres://supportflow:supportflow_local@127.0.0.1:55433/supportflow?sslmode=disable'
go run ./cmd/supportflow
```

`go run` читает переменные процесса, **не загружает `.env` автоматически**. Схема первой версии создаётся при старте под транзакционной блокировкой. Последующие изменения схемы нужно добавлять версионными миграциями.

## Границы MVP

Это локальное рабочее место одного оператора без учётных записей. Порты Compose опубликованы только на loopback. Для внешнего размещения следующий этап — аутентификация, права на обращения, TLS и аудит изменений. При тестировании используйте вымышленные обращения: в режиме `openai` содержимое передаётся внешнему провайдеру.

Дальнейшие учебные шаги: подключить свой API-ключ и вручную оценить ответы; затем добавить авторизацию и историю правок. Интеграцию с почтой или low-code workflow можно добавить после проверки основного сценария.

Остановка с сохранением данных:

```powershell
docker compose down
```

Для просмотра логов: `docker compose logs --tail 100 app`. Тексты обращений, ответы и API-ключ в логи приложения не записываются.
